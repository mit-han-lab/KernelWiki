# NVIDIA H20 (96GB)

H20 is **Hopper/GH100, compute capability 9.0**, not Blackwell. This page
covers the **96GB product listed in NVIDIA's MIG User Guide**. It does not
establish specifications for other capacity variants advertised online.
Hardware identity is officially documented; several peak specifications below
are secondary reports. The tuning checklist is advice to test, not a newly
measured H20 optimization.

## Hardware facts and evidence boundaries

| Property | Value | Evidence |
|---|---|---|
| Architecture / microarchitecture | Hopper / GH100 | NVIDIA MIG User Guide Release 620, chapter 3, Table 1 |
| Compute capability | 9.0 (`sm90` in this wiki) | Same NVIDIA table |
| Listed memory capacity | 96GB | Same NVIDIA table; product capacity, not guaranteed free application memory |
| Maximum MIG instances | 7 | Same NVIDIA table; not seven full-GPU equivalents |
| H20 MIG software requirements | CUDA 12; R535 driver >= 535.161.07 | NVIDIA guide chapters 7 and 10.1; **MIG minimum**, not a universal application/framework requirement |
| Memory type / bandwidth | HBM3 / 4.0 TB/s | Flopper.io secondary specification aggregation |
| Dense BF16 / FP16 Tensor Core peak | 148 TFLOPS | Same secondary aggregation; theoretical, not measured kernel throughput |
| Dense FP8 Tensor Core peak | 296 TFLOPS | Same secondary aggregation; do not compare against sparse peaks |
| TDP | 400W | Same secondary aggregation; not measured board power or a recommended power setting |

The secondary values were **not independently verified against an NVIDIA H20
datasheet**. The cited aggregator itself explains that it has no linked NVIDIA
product datasheet. FP32 peaks are omitted because public secondary tables
disagree. Do not fill gaps with H100's SM count, resource totals, NVLink peak,
or benchmark maxima.

As an illustrative roofline calculation using the secondary dense peaks,
`148 TFLOPS / 4.0 TB/s = 37 FLOP/byte` for BF16/FP16, and FP8 gives
`74 FLOP/byte`. These ratios are theoretical reference points, **not measured
crossovers**. Count actual bytes, conversion/scaling work, and reuse; measure
sustained bandwidth and compute throughput on the target device before
classifying a kernel as memory- or compute-bound.

## Identify the actual device before choosing a kernel

Read-only inspection on the target machine:

```bash
nvidia-smi -L
nvidia-smi --query-gpu=name,uuid,driver_version,memory.total,power.limit --format=csv
nvidia-smi -q
# Where MIG is supported and this read-only query is permitted:
nvidia-smi mig -lgip
```

Use CUDA `cudaGetDeviceProperties` or `cudaDeviceGetAttribute` to record compute
capability, visible multiprocessor count, shared-memory limits, and other
launch constraints. Cache properties outside the timed kernel path. Also
record MIG status, clocks, power limit, CUDA/compiler/library versions, and
whether another workload shares the GPU. On a MIG device, use the resources
visible to that instance rather than full-board assumptions. Inspect supported
profiles locally; this page does not copy H100 profiles onto H20.

No MIG reconfiguration, clock locking, or power-limit changes are implied by
these inspection commands.

## Hopper features and compilation boundaries

- **TMA** performs descriptor-driven asynchronous multidimensional copies.
  Match tensor-map alignment, strides, box size, and shared-memory swizzle to
  the consumer layout. Wait for global-to-shared transaction completion before
  reading or recycling the buffer; shared-to-global copies have different
  completion rules. See `hw-tma` and the Hopper tuning guide.
- **WGMMA** is the Hopper asynchronous warpgroup matrix-multiply path.
  Keep the documented fence, commit/wait, operand-lifetime, and accumulator
  rules. An mbarrier wait for a TMA load alone does not establish that WGMMA
  has finished consuming that buffer. See the PTX ISA and migration guide.
- **Thread-block clusters and mbarrier** are available in Hopper, but launch
  size, occupancy, and shared-memory budgets still constrain a kernel.
  Query occupancy for the actual configuration; a larger cluster or deeper
  pipeline is not automatically faster.
- **Blackwell-specific tcgen05, TMEM, CLC, and native NVFP4 Tensor Core paths
  are not H20 paths.** Software packing/dequantization of FP4 is a different
  claim from native NVFP4 execution.

Compute capability `9.0` identifies the product family; it does not make every
`sm_90` build equivalent to an `sm_90a` build. WGMMA forms require the
architecture-specific target documented by the PTX ISA. Use the library's
Hopper target and runtime dispatch rather than renaming an SM100 kernel.
NVIDIA's compatibility guide states that `sm_90a` / `compute_90a` code is
architecture-conditional; do not assume it is forward-compatible with
Blackwell. Ordinary PTX fallback and architecture-conditional PTX have
different compatibility rules.

## Practical tuning checklist

These are Hopper-informed hypotheses to validate on H20:

1. **Measure the bottleneck for each dtype and shape bucket.** Use a same-device
   library baseline, warm up compilation, and separate kernel timing from
   allocation, dispatch, and preprocessing. Small-M/decode and large-M/prefill
   workloads need not choose the same GEMM tile or schedule.
2. **Reduce bytes when measurements show bandwidth pressure.** Coalesce loads,
   reuse tiles, and consider fusing an epilogue or avoiding a scale transpose.
   Include any quantization, layout conversion, and temporary-buffer cost in
   the comparison. FP8 requires accuracy checks for the actual scaling layout.
3. **Retune tile size, stages, and warp roles together.** More TMA stages or
   producer/consumer warps consume shared memory and registers and can lower
   occupancy. Use actual H20 device attributes and compiler resource reports;
   the H100 resource maxima in NVIDIA's Hopper guide are not H20 measurements.
4. **Size persistent work to the visible GPU.** Inspect active SMs, expert
   token distributions, partial tiles, and the last wave. Compare static,
   persistent, and grouped schedules on the real shape distribution; H20/MIG
   resource counts can change a schedule chosen for H100.
5. **Check correctness before accepting speed.** Cover tails, empty experts,
   irregular groups, strides, and quantization edge cases. If applying an
   inference-derived technique to training, validate backward and all affected
   gradients separately; forward-only evidence is insufficient.

For a performance claim, retain GPU/MIG profile, dtype, full shape and layout,
metric/value, baseline, software/commit versions, timing method, and source.
H100/H800/B200 results in other wiki pages are background, not H20 results.
